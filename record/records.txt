Next feature: User Registration API

We already created the users table and bcrypt password hashing.

Now we need an API that allows a user to create an account.

The flow will be:

Postman
   |
   | POST /auth/register
   | name, email, password
   v
Express
   |
   | hash password with bcrypt
   v
PostgreSQL
   |
   | INSERT user
   v
Express
   |
   | JSON response
   v
Postman

The important part is:

User password
      |
      v
bcrypt.hash()
      |
      v
hashed password
      |
      v
PostgreSQL

We never store the original password.

Create the authentication route:

backend
   |
   +-- routes
       +-- tasks.js
       +-- auth.js

auth.js will contain the registration and login APIs.

Registration endpoint:

POST /auth/register

The request body contains:

{
    "name": "Ruthwik",
    "email": "user@email.com",
    "password": "MyPassword123"
}

The backend receives the password, hashes it, and stores the hash
in PostgreSQL.

The response should contain safe user information and should NOT
return the password.

Registration is now connected:

Postman
   |
   | POST /auth/register
   v
Express
   |
   | bcrypt.hash()
   v
PostgreSQL
   |
   | user stored
   v
Response

Next feature: User Login

Registration creates the account, but we now need to let the user log in.

The flow is:

User
   |
   | email + password
   v
POST /auth/login
   |
   v
Express
   |
   | find user by email
   v
PostgreSQL
   |
   | stored bcrypt hash
   v
bcrypt.compare()
   |
   | password matches
   v
Login successful

The important difference is:

Registration:
password -> bcrypt.hash() -> database

Login:
password + database hash -> bcrypt.compare() -> success/failure

We do NOT decrypt the password.

bcrypt hashes are compared using bcrypt.compare().

If the password is incorrect, the backend returns an error instead
of allowing the user to log in.

Next feature: JWT authentication

JWT means JSON Web Token.

Instead of simply saying "the user logged in", the server gives
the user a token.

The flow becomes:

User logs in
    |
    v
Express verifies password
    |
    v
JWT generated
    |
    v
Token sent to frontend
    |
    v
Frontend stores token
    |
    v
Token sent with protected requests

Example:

Authorization: Bearer <JWT_TOKEN>

The JWT contains information that allows the backend to identify
the authenticated user.

The important idea is:

Login
   |
   v
JWT token
   |
   v
Future API requests
   |
   v
Backend identifies user

Now we need middleware to verify the token.

Create:

backend
   |
   +-- middleware
       +-- authMiddleware.js

The middleware's job is:

Request
   |
   v
authMiddleware
   |
   +-- Is token present?
   |
   +-- Is token valid?
   |
   v
Continue to route

If the token is missing or invalid:

Request
   |
   v
authMiddleware
   |
   v
401 Unauthorized

This allows us to protect routes.

Before authentication:

GET /tasks
    |
    v
all accessible tasks

After authentication:

GET /tasks
    |
    v
JWT
    |
    v
authenticated user
    |
    v
only that user's tasks

This is an important security change.

We now connect the authenticated user's ID to the task queries.

For example:

SELECT * FROM tasks
WHERE user_id = $1

The $1 value comes from the authenticated user's ID.

So now:

User A logs in
    |
    v
JWT contains User A identity
    |
    v
GET /tasks
    |
    v
WHERE user_id = User A
    |
    v
User A's tasks

User B logs in
    |
    v
GET /tasks
    |
    v
WHERE user_id = User B
    |
    v
User B's tasks

This prevents users from simply requesting another user's tasks.

The same ownership check should be applied to task updates and
deletions.

For example:

PUT /tasks/3

should not update task 3 just because the task ID exists.

The backend should verify that task 3 belongs to the authenticated
user.

The security flow is:

JWT
 |
 v
Identify user
 |
 v
Check resource ownership
 |
 v
Allow or reject operation
